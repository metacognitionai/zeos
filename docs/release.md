# Releasing

## Versioning

The version is single-sourced in `pyproject.toml` and bumped only through ordinary
PRs on main, so release history is visible in `git log`. `zeos.__version__` reads
the installed distribution rather than restating the number, and
`tests/contract/test_dist_contents.py` holds the two together.

Releases follow **semver** with a consistent `vX.Y.Z` tag scheme from the first
release onward: the tag matches the `pyproject.toml` version exactly (`v0.1.0` for
`0.1.0`). Release candidates are `X.Y.ZrcN`, and only they may go to TestPyPI.

**Tags are immutable.** A tag is never moved, deleted, or reused. A botched release
gets a new patch version and a new tag, not a re-tag -- anyone who fetched the old
tag must keep seeing exactly what it pointed at.

The same is true on PyPI, more strongly: a filename that has been uploaded can
never be uploaded again, even after deleting it. A bad release is **yanked**, which
hides it from resolvers while leaving it installable by exact pin for anyone who
already depends on it. Deleting is for a file that should never have existed at
all -- a leaked secret -- and it costs that version number permanently.

## Trusted publishing

There is no PyPI API token anywhere in this repository. Both indices are
configured as **trusted publishers**: the workflow presents a short-lived OIDC
token and PyPI checks the repository, its owner id, the workflow's filename and
the environment name before accepting an upload.

| | PyPI | TestPyPI |
| --- | --- | --- |
| Owner | `metacognitionai` | `metacognitionai` |
| Repository | `zeos` | `zeos` |
| Workflow | `release.yml` | `testpypi.yml` |
| Environment | `release` | `testpypi` |

Those four strings are the credential. Renaming a workflow file or an environment
breaks publishing until the publisher is updated to match.

Uploads carry **PEP 740 attestations**, generated by the publish action by
default. They are what lets an installer verify a file came from this workflow in
this repository, so leave them on.

## What is checked, and where

`tests/contract/test_dist_contents.py` builds both distributions and asserts what
they contain: the wheel ships the `zeos` package and nothing else, the sdist can
build it and leaks no secrets, run artifacts or model weights, the licence is both
declared and shipped, the package is attributed, and the two agree on version. It
runs on every CI pass, so a packaging regression fails at the PR that introduces
it rather than at an upload.

The release workflow runs it again against the exact tree being released, then
`twine check --strict` on the built files.

## Releasing

1. **Rehearse.** Bump the version to `X.Y.ZrcN` in `pyproject.toml` and
   `CITATION.cff` on main, then run the `testpypi` workflow by hand. It refuses
   anything that is not a release candidate, publishes to TestPyPI, and then
   installs the candidate into a clean environment from the index and runs the
   determinism gate through the CLI:

   ```bash
   zeos lint <case>
   zeos run <case> --events <events> --journal journal.jsonl --seed 7
   zeos replay journal.jsonl --assert-identical
   ```

   That last command is the gate itself, so the rehearsal proves the published
   artifact keeps the project's flagship guarantee -- not merely that it imports.

2. **Bump to the final version** in `pyproject.toml` and `CITATION.cff`, and let
   it merge with CI green.

3. **Record what CI was green against.** Every `test` job uploads the resolved
   dependency versions for its OS and Python as an artifact. Download the set from
   the green run on the release commit and attach them to the GitHub Release. The
   committed `uv.lock` says what was asked for; these say what was actually
   installed and passed, per platform.

4. **Publish a GitHub Release** on tag `vX.Y.Z`. Use auto-generated notes -- the
   categories come from `.github/release.yml`, and contributor credits come free
   -- and write a short summary above them saying what this release is for.

5. Publishing the Release triggers `release.yml`, which checks the tag against
   `pyproject.toml` and `CITATION.cff`, builds, verifies, and then waits at the
   `release` environment for approval. Approve it.

6. **The smoke job runs itself.** It installs `zeos==X.Y.Z` from PyPI into a clean
   environment and runs the determinism gate through the CLI, against what the
   index actually serves.

## If a release goes wrong

Yank it on PyPI, fix forward with a new patch version, and say in the new
release's notes what the yanked one did. Never delete a file to re-upload it
under the same name; that name is gone either way, and deleting only removes the
copy people can still pin to.
